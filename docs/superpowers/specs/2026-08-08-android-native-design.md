# BiliNote Android 原生客户端设计

## 目标

基于 `BillNote_admin` 的移动页面，构建一个性能稳定、交互一致、同时适配 Android 手机和平板大屏设备的原生客户端。Android 应用只负责客户端体验，视频下载、字幕提取、转写、AI 总结和批量任务继续由现有 BiliNote 后端执行。

## 已确认的产品决策

- Android 端连接现有 BiliNote 后端，服务地址由用户在设置中配置。
- 手机使用底部导航和单列页面。
- 平板使用导航栏；宽屏横屏采用“导航栏 + 列表 + 详情/阅读器”三栏布局。
- 窄屏或竖屏平板采用“导航栏 + 单列内容”，列表通过抽屉或返回选择。
- 笔记正文限制最大阅读宽度，避免平板横向内容过宽。
- 首期覆盖单视频笔记、笔记库、Markdown 阅读、导出和合集任务；不在设备本地执行转写或 AI 生成。

## 参考现状

现有管理端移动页面位于：

- `BillNote_admin/src/MobileApp.tsx`：首页、单视频创建、任务轮询、历史记录、阅读进度恢复和导出。
- `BillNote_admin/src/mobile/MobileBatchWorkspace.tsx`：合集创建、视频选择、详情、追加、重试、日志和批量导出。
- `BillNote_admin/src/api.ts`：统一 JSON 请求、文件上传和二进制下载。

现有后端接口按能力分为：

- 单任务：`/generate_note`、`/upload`、`/task_status/{task_id}`、`/single/tasks`、`/single/tasks/{task_id}/regenerate`、`/export_note/{task_id}`。
- 合集任务：`/batch/preview/*`、`/batch/tasks/*`。
- 模型配置：`/get_all_providers`、`/model_list`。

## 技术方案

采用 Kotlin + Jetpack Compose + Material 3，单一 Android 应用通过窗口尺寸自适应实现手机和平板布局，不维护两套 UI。

核心技术：

- Compose、Material 3、Navigation Compose。
- `WindowSizeClass` 识别 compact、medium、expanded 窗口。
- ViewModel + StateFlow 管理页面状态。
- Retrofit/OkHttp + Kotlin Serialization 访问后端。
- Room 缓存任务、历史笔记摘要和阅读进度。
- WorkManager 执行可恢复的上传与后台同步。
- Hilt 管理依赖。
- Markdown 渲染组件配合 Coil 完成图片缓存和笔记阅读。

## 模块边界

```text
app
core:network
core:database
core:designsystem
feature:home
feature:batch
feature:library
feature:reader
feature:settings
```

- `core:network`：服务地址、请求封装、错误码、接口 DTO、上传和下载。
- `core:database`：Room 表、DAO、缓存策略和阅读进度。
- `core:designsystem`：颜色、排版、间距、按钮、状态标签和响应式容器。
- `feature:*`：各页面的 ViewModel、Repository 接口和 Compose UI。
- `app`：依赖组装、导航图、窗口尺寸分发和应用生命周期。

各 feature 不直接操作 Retrofit 或 Room，只依赖 Repository，便于离线缓存和测试替换。

## 页面与响应式布局

### 首页

手机显示创建入口、进行中任务、继续阅读和最近笔记；平板宽屏可将创建/任务区域与最近笔记并排展示。创建任务使用底部抽屉或宽屏 ModalPane。

### 合集

手机使用合集卡片列表，详情进入全屏页面；平板宽屏使用三栏：导航栏、合集/视频列表、子任务详情。详情支持整体进度、子任务状态、日志、阅读、导出、重试、删除和追加。

### 笔记库

手机使用单列历史列表；平板宽屏使用笔记列表 + 阅读器双栏。处理中、失败和已完成状态必须有明确的颜色、文案和可用操作。

### 阅读器

手机为全屏沉浸式阅读；平板宽屏保留列表或目录，右侧展示正文。正文最大宽度约 720dp，支持标题层级、列表、代码、图片、时间链接、来源链接、导出和阅读进度恢复。

### 设置

设置服务地址、连接测试、缓存管理、版本信息和打开桌面管理端。服务地址需要统一规范化，至少校验 HTTP/HTTPS、主机名和尾部斜杠。

## 数据流和任务同步

```text
Compose UI
  -> ViewModel / StateFlow
  -> Repository
  -> Room cache + Retrofit API
```

任务状态采用生命周期感知同步：

- 页面前台且任务进行中：约 2.5～5 秒拉取一次状态。
- 页面进入后台：停止高频轮询，保留最近状态。
- 应用重新进入前台：立即刷新相关任务。
- Room 保存最后一次状态、标题、平台、任务时间和阅读进度。
- 服务器不可用时展示缓存内容和离线提示，不清空已有数据。

当前后端主要是串行任务执行器，因此客户端不应通过并发轮询制造额外压力；多个任务列表刷新应合并请求并避免重复触发。

## 性能与交互要求

- 所有网络、文件和数据库操作运行在协程，不阻塞主线程。
- 任务和历史列表使用 `LazyColumn`，不一次性创建全部子项。
- 历史列表首期缓存最近 50 条，详情按需读取。
- Markdown 图片使用磁盘/内存缓存，失败图片显示可重试占位。
- 本地视频通过 Storage Access Framework/Photo Picker 选择，不依赖永久文件路径。
- 上传支持进度、取消和失败重试；后端若无法断点续传，客户端至少保留可重试任务状态。
- 阅读进度按节流策略写入 Room，避免每次滚动事件写库。
- 使用 Baseline Profile、Macrobenchmark 和真机滚动测试优化首屏、列表和阅读器。
- 触控目标不小于 48dp，支持系统字体放大和横竖屏切换。

## 错误处理

- 连接失败：显示服务地址、网络状态和重试入口。
- 认证失败：清晰提示 Token 或权限问题，不显示底层堆栈。
- 任务失败：展示后端 message，支持重试；失败任务不能误显示为可阅读。
- 结果缺失：状态为成功但正文不存在时降级为“结果同步中”，允许刷新。
- 导出失败：保留当前页面状态，允许重新导出。
- 服务地址变化：清理旧服务的任务缓存，避免跨服务混淆。

## 后端配合项

首期可复用现有接口，但正式发布前需要确认：

1. 公网部署必须使用 HTTPS。
2. 建议补充用户认证或访问 Token；当前接口看起来没有明显认证层。
3. 明确上传文件大小、超时和错误码。
4. 确认图片、上传文件和导出文件的访问权限。
5. 若需要可靠后台上传，再增加分片上传或断点续传接口。

这些是发布安全和可靠性检查项，不改变 Android 客户端只连接后端的总体架构。

## 实施阶段

### 阶段 0：接口与安全基线

确认服务地址、认证、错误码、上传限制、图片访问和导出权限。

### 阶段 1：Android 基础壳

建立 Compose 工程、主题、响应式导航、设置页、服务地址配置、连接测试和基础网络层。

### 阶段 2：单视频闭环

实现创建任务、链接/本地视频选择、上传、任务状态、失败重试和首页任务卡片。

### 阶段 3：笔记库与阅读器

实现历史列表、Markdown 渲染、图片、时间链接、导出、阅读进度和 Room 缓存。

### 阶段 4：合集能力

实现合集预览、创建、详情、子任务日志、重试、删除、追加和批量导出。

### 阶段 5：大屏和质量优化

完成三栏布局、断网恢复、后台同步、无障碍、性能基准、真机适配和发布检查。

## MVP 验收标准

- 手机和平板均可配置服务地址并完成连接测试。
- 手机可以创建单视频任务，查看进度，失败后重试并阅读结果。
- 平板横屏能同时显示导航、笔记列表和阅读器。
- 阅读器支持 Markdown、图片、导出和阅读进度恢复。
- 应用重启后仍能显示缓存历史和未完成任务的最新状态。
- 网络异常不会导致已缓存笔记丢失或 UI 卡死。
- 关键页面通过单元测试、Repository 网络测试、Compose UI 测试和真机性能测试。

## 非目标

- 不在 Android 设备本地运行 Whisper、视频下载或 AI 模型。
- 不在首期重写现有后端任务系统。
- 不复制桌面管理端的全部配置功能；模型供应商等配置继续由管理端维护。
- 不为手机和平板维护两套业务逻辑或两套接口层。
